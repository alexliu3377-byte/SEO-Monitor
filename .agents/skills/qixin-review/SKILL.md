先读项目根目录 AGENTS.md、CLAUDE.md，再读 [共享审核规范](../../../docs/REVIEW_AND_RELEASE.md)。根据用户指定范围选择审核维度，不默认扫描生产或启动采集。用户本轮明确指令和已有授权优先于本技能的默认流程。

## 选择审核角色

这些是 Codex 可复用的审核技能，不是常驻服务，也不代表已经启动多个独立 Agent。默认由当前会话按范围执行；只有用户明确要求并行或独立复核且工具支持时才委派。委派时说明仓库、比较基线、允许读取的环境和只读边界；汇总者复核发现，不按角色数量投票。

| 用户需求 | 读取的角色 |
| --- | --- |
| 代码变更、越权、接口、数据库适配 | [代码与安全](../qixin-code-review/SKILL.md) |
| 抓取失败、空数据、日期、去重、任务调度 | [采集与数据](../qixin-collection-review/SKILL.md) |
| CPU、缓存、轮询、运行环境、部署状态 | [性能与运行](../qixin-runtime-review/SKILL.md) |
| 全面系统体检 | 以上三个角色，逐项报告覆盖情况 |
| 发布验收 | 按改动选择角色，并执行共享规范的发布判定；不执行发布 |

单项请求只加载相关角色。代码改动审核先确认 git status、分支、HEAD 和比较基线；未指定时优先审查未提交改动，没有改动则检查最近提交并明确范围。全面体检不局限于最新 diff。不要仅为确定基线自动合并或重置分支。

## 证据与结果

每项发现记录：优先级、确认/待验证、触发条件、文件行号或运行链接与时间、影响、最小修复建议及验证方法。P0 为正在发生的严重事故，P1 为应优先修复的高影响问题，P2 为普通缺陷，P3 为低影响改进。没有实际证据的可能性放在待验证项，不作为确认缺陷。

汇总时合并同一根因的重复发现，列出实际检查范围、执行的命令与结果、缺失权限或证据。区分代码、本地测试、数据库适配、推送、部署和线上验证；没有新问题时可明确说明“本次范围未发现新问题”，同时保留覆盖限制。历史报告只是定位线索，旧的采集数量和 CPU 数值不可直接当作本次结论。

默认在对话输出结果；用户需要报告时再写入指定文件。只做审核不顺手修复，不提交、推送、触发任务或发布内容。若用户同时授权修复，按其范围处理并单独说明修复后验证结果。

数据库审核以本次涉及对象和授权取得的结构证据为边界；schema.sql 是不完整历史快照。缺少结构、权限或迁移生效证据时标为未验证，不能补执行 SQL 来“通过”检查。

项目有独立 Worker 和已运行的 Windows 采集任务。主项目检查不能替代 Worker 检查，修改开发副本不能视为运行副本已更新。

报告列出可定位文件、触发条件、影响、证据和建议，区分已确认问题与待验证风险。性能数值需要实测依据；审核通过不授权发布。
