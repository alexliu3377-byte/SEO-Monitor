# 已提交内容覆盖

入口：成效报告，进入分组后右上方「覆盖名称」。

1. 粘贴完整链接，查找当前分组所有成员的已提交记录（20 条/页）。
2. 选中一条记录，输入这次实际做的覆盖词，确认后保存。
3. 同一个链接的其它提交不会一起被修改。普通报告仍只让组员看自己的记录。

覆盖行为：原记录 ID、URL、分组、创建时间保持不变；操作类型改为「覆盖」，关键词和最终词均改为覆盖词，成员改为实际登录操作人员，认领/提交日期更新为马来西亚当天，提交时间为当前时刻，来源改为「手动添加」，解除原分发规则归属。按覆盖词精确匹配 `keyword_volume`；没有匹配则搜索量为 0（界面说明未匹配），不沿用旧词的搜索量，也不发起外部搜索抓取。成效筛选提供独立的「覆盖」选项，得分使用增量口径，不把既有页面当作新内容计分。

原名称、原成员、原日期和覆盖操作人员/时间保存在独立的 `submission_overwrite_history`，可在选中记录后查看分页历史。同日被替换的追踪快照也备份到历史中，旧日的追踪和排名证据不删除。

数据库权限与登录校验两层防护；只有当前分组成员、获得该组站点权限的管理员及超级管理员可使用。查找接口只接受完整页面链接，不提供无条件读取全部成员记录的接口。数据库重新检查权限与原记录指纹，阻止并发或过期结果覆盖。词/当天提交冲突时整笔操作回滚，历史与缓存都不改变。

覆盖后原成员的旧缓存立即失效，优先沿用其它条目的有效缓存，仅重算被修改记录的排名证据与分组汇总。并发的旧缓存写回会被阻止；在途爬虫也不能把旧成员、旧名称写回当前追踪记录。缓存刷新失败不伪装成覆盖失败，页面明确区分「覆盖成功，缓存待刷新」。

部署需单独应用 `supabase/migrations/20261014_submission_overwrite.sql`，不要顺便应用其它待提交迁移。代码改动未部署前不会产生真实覆盖。
