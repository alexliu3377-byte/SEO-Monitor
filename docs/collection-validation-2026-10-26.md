建议后续分别记录 source_date、collected_at／batch_date，并校验来源页实际日期。是否用发现日还是来源日展示，应遵守各业务 Tab 的既定含义，不能全库统一倒移一天。

## 五、LangGraph JS 与 Mastra：同样本首轮比较

没有调用 LLM。两个框架执行相同宿主规则，使用：

1. 已保存的指定 B 站字幕，注入一次临时读取异常，观察是否只重试读取步骤。
2. 真实 18touch 日期解析异常记录，要求暂停待审核并支持拒绝。
3. 已核实的爱站来源日／批次日差异，要求暂停确认，不自动写生产资料。

两者均通过：

- 成功步骤执行一次，失败读取步骤执行两次。
- 实际暂停并恢复；拒绝后结果为 blocked。
- 审核节点在恢复时重新执行，最终本地记录步骤只执行一次。
- 重复恢复没有重复执行最终记录。LangGraph 返回已有结果，Mastra 拒绝重复恢复。

LangGraph 审批参数需要使用明确的对象如 approved=false，而不是直接把 false 当整个 resume 输入；本轮首次试验暴露了裸 false 被视为空命令的适配问题，改为结构化对象后通过。

仅为同进程、内存存储试验。持久化、进程重启、断电、多 Worker 并发、真实网络长期失败均未验收；失败注入不代表历史 B 站异常已经修复。异常识别规则是我们提供的，不是框架自己判断事实。

当前更适合继续评估 LangGraph JS：可作为薄执行层包住现有工具，不必新增另一套后台。Mastra 同样可行，若后续确实需要其完整 Agent 管理能力，再比较综合成本。不能依据此次毫秒级试验直接宣称生产性能优劣。

## 六、Crawlee：有用的地方与不能解决的地方

对三份真实来源页面做本机 HTTP 回放，不再次访问来源站。同一个请求重复入队两次：

- pcsoft 实际请求一次；相同选择器仍得到 0 条。
- niucoo 实际请求一次；相同选择器仍选中 34 个候选，仍含 14 个非内容入口。
- 18touch 注入一次本机 HTTP 503 后请求两次，自动重试成功；相同选择器仍有 36 个旧规则无法解析的时间。

因此 Crawlee 已验证的价值是请求去重、有限重试及队列管理，不是自动修正业务选择器或日期。

另做试验性业务校验后，niucoo 一页过滤掉 14 个分类入口；18touch 的 36 个带后缀相对时间可被解析。这些是我们额外的规则修正，不是 Crawlee 自带效果，也尚未应用到生产。

未测试浏览器挑战、验证码或出口 IP；不能声称换 Crawlee 后就能解决百度验证。26 日百度收录日志中多个站点仍有验证拦截，应明确标 blocked，与真实空结果区分。

隔离依赖当次 npm audit 为 0 个已知告警，仅代表该次注册表结果，不构成长期安全保证。

## 七、建议先后顺序

1. 先修日期解析／未知日期兜底、分类入口过滤和已失效选择器。
2. 明确爱站来源日和采集日两个字段，区分空榜、受限和失败。
3. 单独检查四条 B 站历史异常是否值得重试，并保留原文与字幕来源。
4. 原有采集规则稳定后，再以 LangGraph 做持久化恢复验证；Crawlee 只选一个来源接入。
5. Promptfoo 暂放；不急于生成改写文章或自动发布。
