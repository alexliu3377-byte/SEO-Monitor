# 应用更新中心：v4.0.0 超管实验

这一阶段先在正式网站建立一个独立的实验后台，用来登记应用和公开更新页面、运行 GitHub Actions 抓取、人工审核结果并导出 CSV。它不会下载或保存 APK、安装包、图片和视频。

## 1. 建立数据库

在 Supabase SQL Editor 运行：

`supabase/migrations/20260910_app_update_center_foundation.sql`

成功后不需要新增 Supabase 密钥。GitHub Actions 继续使用项目已有的：

- `NEXT_PUBLIC_SUPABASE_URL`
- `SUPABASE_SERVICE_ROLE_KEY`

## 2. 部署网站

推送代码并等待 Vercel 部署完成。只有角色为 `super` 的账号会在原系统侧边栏看到“进入应用更新中心”。组员和管理员没有入口，直接访问页面或 API 也会被拒绝。

## 3. 登记第一个应用

进入“应用更新中心”，点击“新增应用”，填写：

- 应用名称和平台
- 包名或应用标识（不知道可以先留空）
- 来源名称和类型
- 一个不需要登录即可打开的公开更新页面 URL

同一应用可以添加多个来源。第一轮建议只登记 1 至 3 个你熟悉的应用，先比较官方网站、应用商店或下载站中哪一种页面最稳定。

## 4. 手动运行抓取

点击页面右上角“打开抓取任务”，进入 GitHub Actions 的 `App update crawl`：

1. 点击 `Run workflow`。
2. `app_id` 留空会检查所有启用来源；填写页面中的应用 UUID 时只检查一个应用。
3. `limit` 是本轮最多检查多少个来源，实验初期保留默认值即可。
4. 任务结束后回到应用更新中心刷新页面。

抓到的新版本默认进入“待审核”。确认版本号和更新日志后点击“通过”，它才会成为该应用当前认可的最新版本；错误资料可以“忽略”。

## 5. 导出资料

在更新记录中勾选需要的版本，再点击“导出”。单次最多导出 200 条 UTF-8 CSV，可直接用 Excel 打开。

## 当前限制

- 各网站页面结构不同，通用识别不可能一次覆盖全部来源。
- 页面没有公开更新日志、内容依赖登录或完全由复杂脚本生成时，可能识别失败。
- 当前不自动定时运行；先通过手动任务验证来源稳定性和识别准确率。
- 当前不抓取安装包本体，也不承诺下载链接长期有效。
- 运行失败时先看“抓取记录”和来源错误；稳定后再为常用站点增加专用解析规则。
